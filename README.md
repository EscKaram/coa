## 0. Решения, оставленные условием на усмотрение автора

Требования ниже опираются на эти решения. Все отметки времени хранятся в UTC. Тихие часы вычисляются по часовому поясу клиента из профиля.

### 0.1. Какие уведомления можно отключить

| Тип | Примеры | Можно отключить? | Каналы | Тихие часы, лимит частоты |
|---|---|---|---|---|
| Транзакционные (критичные) | списание, перевод, зачисление, вход с нового устройства, смена пароля | **Нет.** Клиент выбирает только основной канал: push или SMS. Резервные каналы не отключаются | push → SMS → email (порядок задаёт выбранный основной канал) | не применяются |
| Сервисные | статус заявки на кредит, напоминание о платеже, перевыпуск карты | **Да**, по категориям и по каналам. Исключение: юридически значимые сообщения (изменение условий договора, тарифов). Они всегда уходят минимум по одному каналу | push, email; SMS только для юридически значимых | тихие часы 21:00–09:00 по времени клиента, кроме юридически значимых |
| Маркетинговые | акции, кэшбэк, предложения продуктов | **Да**, полностью или по каналам. Отписка в один клик. Рассылка по SMS и email только при согласии клиента на рекламу | push, email, SMS (только с согласием) | тихие часы 21:00–09:00; не более N в сутки (N настраивается, по умолчанию 5, что соответствует средней нагрузке из условия) |

Почему транзакционные отключить нельзя: клиент должен узнавать о движении средств, чтобы вовремя заметить мошенничество. Это задача безопасности, а не маркетинга. Кроме того, «нет централизованного контроля и невозможно гарантировать доставку» — одна из исходных проблем.

### 0.2. Уровни сервиса

| Тип | Целевое время доставки | Гарантия |
|---|---|---|
| Транзакционные | передача провайдеру ≤ 1 с (p99), доставка хотя бы по одному каналу ≤ 5 с (p95) и ≤ 30 с (p99) с учётом failover | хотя бы один канал, автоматический failover, сообщение не теряется |
| Сервисные | ≤ 60 с (p95) | at-least-once в выбранный канал, повторы при сбое провайдера, без кросс-канального failover |
| Маркетинговые | по расписанию кампании; кампания на 1 млн получателей отправляется за ≤ 30 мин | best effort: при сбое провайдера повторы ограничены, после истечения TTL сообщение отменяется |

Что значит «доставлено» (подробнее в RFC, раздел [«Что считается доставкой»](docs/rfc-001-guaranteed-delivery.md#что-считается-доставкой-таймауты-и-повторы)): для push это подтверждение от мобильного приложения (ack), для SMS — статус DELIVERED в отчёте о доставке (DLR), для email — событие `delivered` от провайдера (письмо принял почтовый сервер получателя).

### 0.3. Общая схема платформы

Схема нужна как контекст для §4–§6. Подсистема гарантированной доставки подробно разобрана в RFC.

```
Продуктовые сервисы ──outbox──▶ Kafka ──▶ Ingest (валидация, дедупликация, настройки, шаблоны)
(платежи, переводы,                              │
 кредиты, акции)                                 ├─▶ транзакционные: оркестратор доставки с failover (RFC)
Campaign Manager ─── сегмент 1 млн ──────────────┼─▶ сервисные:     очередь с повторами
                                                 └─▶ маркетинговые: очередь кампаний с rate limit
                                                               │
                                    Channel Senders: push │ SMS (2+ провайдера) │ email
                                                               │
                         Receipt Collector ◀── DLR / ack ── провайдеры и мобильное приложение
                                                               │
                           история и статусы (поддержка) · аналитика (ClickHouse) · метрики и трейсы
```

## 1. Функциональные требования

Формат: user story, критерий приёмки, связь с бизнес-целью. Бизнес-цели: **R** — retention +15%, **C** — жалобы −30%, **G** — гарантированная доставка критичных уведомлений.

| ID | Требование | Критерий приёмки | Цель |
|---|---|---|---|
| FR-1 | **Единая точка приёма.** Как продуктовая команда, я передаю платформе уведомление с типом, категорией, получателем, шаблоном и ключом идемпотентности, чтобы не реализовывать доставку самостоятельно | все уведомления банка проходят через платформу; продюсер получает идентификатор уведомления и может узнать его финальный статус | C, G |
| FR-2 | **Гарантированная доставка транзакционных.** Как клиент, я узнаю о каждом списании и переводе хотя бы по одному каналу, даже если основной канал недоступен | если основной канал не подтвердил доставку, система сама отправляет уведомление по следующему каналу; если все каналы исчерпаны, создаётся инцидент для поддержки | G |
| FR-3 | **Управление подписками.** Как клиент, я выбираю, какие сервисные и маркетинговые уведомления и по каким каналам получать, и выбираю основной канал для транзакционных | настройки применяются к уведомлениям, созданным после изменения; транзакционные отключить нельзя (§0.1) | C, R |
| FR-4 | **Одно событие — одно уведомление.** Как клиент, я не получаю повторов одного уведомления, даже если продуктовый сервис отправил запрос несколько раз | повторный запрос с тем же ключом идемпотентности не приводит к повторной отправке | C |
| FR-5 | **Приоритет критичных.** Как клиент, я получаю уведомление о списании сразу, даже во время массовой рассылки | транзакционные уведомления не ждут в очереди за маркетинговыми и сервисными | G, C |
| FR-6 | **Массовые кампании.** Как маркетолог, я запускаю кампанию на сегмент до 1 млн клиентов по расписанию, вижу прогресс и могу её остановить | кампания учитывает подписки, согласия, тихие часы и лимиты частоты; после остановки новые отправки прекращаются | R |
| FR-7 | **Тихие часы и лимиты частоты.** Как клиент, я не получаю рекламу ночью и не получаю её слишком часто | маркетинговые и несрочные сервисные уведомления в тихие часы откладываются до утра по времени клиента; лимит в сутки соблюдается по всем каналам вместе | C |
| FR-8 | **История и статусы.** Как сотрудник поддержки, я вижу все уведомления клиента: каналы, попытки, причины неудач, время доставки | по жалобе «не пришло» поддержка находит уведомление и причину без обращения к разработчикам | C, G |
| FR-9 | **Аналитика эффективности.** Как маркетолог, я вижу доставку, открытия и конверсию по кампаниям, каналам и сегментам | отчёт по кампании доступен на следующий день или раньше | R |
| FR-10 | **Отписка в один клик.** Как клиент, я отписываюсь от маркетинговой рассылки прямо из письма, SMS или push | отписка вступает в силу для следующих отправок этой рассылки | C |

## 2. Нефункциональные требования

Числа — решения автора, если не сказано иное. Пиковая нагрузка 1 000 транзакционных уведомлений/с выведена в RFC (раздел [«Расчёт нагрузок»](docs/rfc-001-guaranteed-delivery.md#расчёт-нагрузок)) из MAU/DAU, указанных в условии; там же перечислены допущения.

| ID | Атрибут | Требование | Как измеряется |
|---|---|---|---|
| NFR-1 | Performance (задержка платформы) | Транзакционные: от приёма до передачи провайдеру первого канала p95 ≤ 300 мс, p99 ≤ 1 с при 1 000 уведомлений/с | гистограмма `accepted_at → submitted_at` по типам |
| NFR-2 | Performance (сквозная задержка) | Транзакционные: от приёма до подтверждённой доставки хотя бы по одному каналу p95 ≤ 5 с, p99 ≤ 30 с с учётом failover. Сервисные: p95 ≤ 60 с | гистограмма `accepted_at → delivered_at`. Знаменатель: уведомления клиентов, у которых есть хотя бы один действующий контакт |
| NFR-3 | Reliability (гарантия доставки) | 0 потерянных транзакционных уведомлений после подтверждения приёма (RPO = 0). 100% уведомлений приходят в конечный статус (`DELIVERED` или `UNDELIVERED`) не позже чем через 24 ч. Не менее 99,9% доставлены за ≤ 15 мин (с учётом резервного email) | ежедневная сверка: число принятых равно сумме доставленных и недоставленных; доля «зависших» = 0 |
| NFR-4 | Availability | Приём транзакционных: 99,95% в месяц (≤ 21,6 мин простоя за 30 дней). Сервисные и маркетинговые: 99,5% (≤ 3,6 ч). Отказ одной зоны доступности (AZ) не останавливает приём и доставку транзакционных; RTO stateful-компонентов ≤ 5 мин | доля успешных запросов на приём; учения с отключением AZ |
| NFR-5 | Scalability / throughput | Транзакционные: 1 000/с постоянно, всплески до 2 000/с длительностью до 5 мин. Кампания на 1 млн получателей за ≤ 30 мин (≈ 556/с) без нарушения NFR-1. Рост ×3 закрывается горизонтальным масштабированием без смены архитектуры | нагрузочный тест: смесь транзакционного пика и кампании на 1 млн |
| NFR-6 | Отсутствие дублей | Повторный запрос продюсера с тем же ключом в окне 7 суток не приводит к повторной отправке (0 повторов). Дубли в одном канале на устройстве ≤ 0,01%. Кросс-канальные дубли (подтверждение по первому каналу пришло после старта резервного) ≤ 2% транзакционных | счётчики повторных ключей и поздних подтверждений |
| NFR-7 | Fault tolerance (провайдеры) | При отказе одного SMS- или email-провайдера трафик переключается на резервного за ≤ 30 с без потерь. Повторы не превышают квоту провайдера | хаос-тест: недоступность провайдера, ответы 5xx, таймауты |
| NFR-8 | Observability | Статус и история любого уведомления доступны поддержке не позже чем через 60 с после события. Метрики задержки и доставки по типу, каналу и провайдеру с разрешением ≤ 1 мин. Алерт о сгорании бюджета ошибок SLO — в течение ≤ 5 мин | время появления события в истории; время срабатывания алертов на учениях |
| NFR-9 | Cost efficiency | Доля транзакционных уведомлений, ушедших по SMS, ≤ 35% (оценка в RFC — около 29%). Расходы на SMS видны ежедневно в разрезе команд-продюсеров | дневной отчёт по каналам и продюсерам |
| NFR-10 | Security / ПДн | Телефоны, email и тексты шифруются при хранении и передаче (TLS 1.2+). В логах нет ПДн (маскирование). Каждый доступ к истории фиксируется в аудите. Соответствие 152-ФЗ | автоматическая проверка логов на ПДн: 0 находок; 100% обращений к истории в аудите |

## 3. Архитектурно значимые требования (ASR)

Приоритет: **P1** — без выполнения требования система не решает исходную задачу; **P2** — существенно влияет на устройство системы; **P3** — важно, но слабее ограничивает выбор архитектуры.

### ASR-1 [P1]. Гарантированная доставка критичных уведомлений с автоматическим failover

**Связанные требования:** FR-2, FR-8, NFR-3, NFR-4.

**Почему влияет на архитектуру.** «Хотя бы по одному каналу, без потерь» нельзя добавить к готовой системе: это свойство всей цепочки обработки. Состояние каждого уведомления (какой канал пробовали, сколько ждать подтверждения) должно храниться надёжно и переживать рестарты. Таймеры ожидания подтверждения тоже должны быть надёжными, а не жить в памяти процесса. Каждая передача между компонентами должна работать по схеме at-least-once с подтверждением. Продюсеры должны передавать событие без потерь (transactional outbox). Отсюда следуют модель хранения, модель взаимодействия (асинхронная, с подтверждениями) и необходимость оркестратора доставки.

### ASR-2 [P1]. Низкая задержка транзакционных при пике и во время массовых кампаний

**Связанные требования:** FR-5, NFR-1, NFR-2, NFR-5.

**Почему влияет на архитектуру.** p99 ≤ 1 с должен выполняться при 1 000/с одновременно с кампанией на 1 млн. Поэтому транзакционный трафик изолируется на всех уровнях: отдельные очереди, отдельные пулы обработчиков, зарезервированные квоты у провайдеров. На горячем пути минимум синхронных вызовов: настройки клиента читаются из кеша, нет пакетной обработки (батчинга), нет ожидания других типов трафика.

### ASR-3 [P1]. Отсутствие дублей при повторах и failover

**Связанные требования:** FR-4, NFR-6.

**Почему влияет на архитектуру.** Гарантия at-least-once (ASR-1) сама порождает повторы: повторяют продюсеры, повторяют внутренние компоненты, повторяет failover. Чтобы клиент видел одно уведомление, нужны:

- сквозные ключи идемпотентности от продюсера до провайдера;
- один владелец состояния уведомления и атомарные условные переходы этого состояния;
- не более одного активного канала в каждый момент;
- склейка повторов на устройстве (collapse-id).

ASR-1 и ASR-3 нужно решать вместе, по отдельности они противоречат друг другу.

### ASR-4 [P2]. Устойчивость к нестабильным внешним провайдерам

**Связанные требования:** NFR-7, FR-2, NFR-3.

**Почему влияет на архитектуру.** Внешний провайдер — точка отказа, которую мы не контролируем. Поэтому нужны несколько провайдеров на канал, а адаптер каждого провайдера — отдельный компонент со своими circuit breaker, rate limiter и бюджетом повторов. Сбой провайдера не должен блокировать остальной трафик (bulkhead).

### ASR-5 [P2]. Масштабирование под массовые кампании до 1 млн получателей

**Связанные требования:** FR-6, NFR-5.

**Почему влияет на архитектуру.** Кампания на 1 млн за ≤ 30 мин требует ≈ 556 отправок/с поверх обычного трафика, а сегментация и рендеринг шаблонов выполняются миллион раз. Это задаёт асинхронный конвейер с партиционированием, горизонтальным масштабированием обработчиков и управляемой скоростью отправки. Конвейер кампаний отделяется от транзакционного (см. ASR-2).

### ASR-6 [P2]. Минимальная стоимость доставки при сохранении гарантии

**Связанные требования:** NFR-9, FR-3, FR-2.

**Почему влияет на архитектуру.** SMS значительно дороже push, поэтому failover последовательный: сначала push, SMS — только если push не подтвердился. Параллельная отправка во все каналы не подходит. Это прямо конфликтует с ASR-2: каждое ожидание подтверждения push добавляется к задержке. Нужны механизм ожидания с надёжным таймером, данные о достижимости устройства и маршрутизация по стоимости между SMS-провайдерами.

### ASR-7 [P3]. Сквозная наблюдаемость процесса доставки

**Связанные требования:** FR-8, FR-9, NFR-8.

**Почему влияет на архитектуру.** Каждое изменение состояния уведомления должно фиксироваться как событие с единым идентификатором и trace-контекстом во всех компонентах. Нужно отдельное аналитическое хранилище для истории и отчётов, чтобы аналитические запросы не нагружали оперативную БД. Состояния должны быть явными, чтобы их можно было наблюдать.

## 4. Ключевые архитектурные вопросы

| ID | Вопрос | Порождают | Почему важен |
|---|---|---|---|
| Q-1 | **Что считать доставкой и когда переключаться на резервный канал?** Какие подтверждения у каждого канала и какие таймауты ожидания | ASR-1, ASR-3, ASR-6, NFR-2 | Таймаут ожидания push задаёт баланс трёх величин. Короткий таймаут — быстрая доставка, но больше SMS (стоимость) и больше поздних подтверждений (дубли). Длинный — дешевле, но медленнее. Без явного определения доставки гарантию нельзя ни выполнить, ни измерить |
| Q-2 | **Где хранить состояние доставки и как реализовать надёжные таймеры?** Собственный автомат состояний (state machine) поверх БД и брокера или workflow-движок | ASR-1, ASR-2, ASR-3 | От ответа зависят основная технология подсистемы, нагрузка на хранилище, сложность разработки и эксплуатации. Это главный выбор в RFC (разделы «Варианты решения» и «Выводы») |
| Q-3 | **Как изолировать транзакционный трафик от массовых кампаний?** Отдельные топики, пулы, кластеры, квоты провайдеров | ASR-2, ASR-5, NFR-5 | Общая очередь даёт head-of-line blocking: кампания на 1 млн задержит списания на минуты. Изоляция определяет топологию брокера и развёртывание |
| Q-4 | **Как продюсеры передают уведомления: синхронно или асинхронно, и как гарантировать, что событие не потеряется на стороне продюсера?** | ASR-1, ASR-3, FR-1 | Если списание прошло, а уведомление не отправилось из-за падения сервиса между коммитом и вызовом, гарантия нарушается до входа в платформу. Ответ определяет контракт для всех команд банка: outbox, ключ идемпотентности |
| Q-5 | **Где применять настройки клиента: при приёме или перед отправкой, и насколько свежими они должны быть?** | FR-3, ASR-2, FR-7 | Чтение настроек при каждой отправке нагружает сервис настроек. Устаревший кеш означает отправку тому, кто только что отписался, а это жалоба. Ответ определяет кеширование и распространение изменений (CDC) |
| Q-6 | **Как распределять трафик между SMS-провайдерами и когда считать провайдера недоступным?** | ASR-4, ASR-6, NFR-7 | Маршрутизация влияет на стоимость, задержку и дубли. Если провайдер ответил таймаутом, неизвестно, отправил ли он SMS. Повтор через другого провайдера может дать дубль |

## 5. Архитектурные последствия ASR

**ASR-1. Гарантированная доставка**
- Надёжное хранение состояния каждого уведомления и попытки (БД с синхронной репликацией, RPO = 0).
- Надёжные таймеры ожидания подтверждения, которые переживают рестарт обработчика.
- Асинхронное взаимодействие через брокер с подтверждением записи (Kafka `acks=all`, `min.insync.replicas=2`).
- Transactional outbox у продюсеров и внутри платформы: состояние и исходящее сообщение пишутся в одной транзакции.
- Явный автомат состояний уведомления с конечными статусами и процесс сверки (reconciliation), который находит «зависшие» уведомления.
- Несколько каналов и несколько провайдеров на канал.

**ASR-2. Низкая задержка транзакционных**
- Отдельные топики, группы потребителей и пулы обработчиков для транзакционного трафика (bulkhead).
- Зарезервированная доля квоты провайдеров под транзакционные сообщения.
- Кеш настроек и контактов (Redis) на горячем пути; изменения распространяются через CDC.
- Без пакетной обработки на транзакционном пути; заранее известный бюджет задержки по шагам.
- Автомасштабирование по лагу потребителей.

**ASR-3. Отсутствие дублей**
- Детерминированный идентификатор уведомления из ключа идемпотентности продюсера и уникальное ограничение в БД.
- Условные атомарные переходы состояния (compare-and-set по версии): из гонки «подтверждение против таймаута» выходит победителем ровно одно событие.
- Последовательный failover: команда для следующего канала создаётся в той же транзакции, что закрывает предыдущую попытку.
- Ключ попытки передаётся провайдеру как client message id; `apns-collapse-id` и FCM `collapse_key` склеивают повторы push на устройстве.
- Метрика поздних подтверждений и калибровка таймаутов по ней.

**ASR-4. Нестабильные провайдеры**
- Адаптер на каждого провайдера с circuit breaker, rate limiter (token bucket) и ограниченными повторами с экспоненциальной задержкой и jitter.
- Минимум 2 SMS-провайдера; email — провайдер рассылок и собственный SMTP-релей как резерв.
- Health score провайдера (доля успешных DLR, задержка) влияет на маршрутизацию.
- Сбои провайдера изолированы от остальных каналов и типов трафика.

**ASR-5. Массовые кампании**
- Асинхронный конвейер: сегмент → партиции → рендеринг → отправка.
- Партиционирование по `user_id` и горизонтальное масштабирование обработчиков.
- Управляемая скорость отправки (throttling) под квоты провайдеров и тихие часы.
- Кампанию можно приостановить и продолжить; прогресс хранится по партициям.

**ASR-6. Минимальная стоимость**
- Последовательная политика каналов «push → SMS → email» вместо параллельной рассылки.
- Учёт достижимости устройства: если у клиента нет действующего push-токена или push давно не подтверждался, первым каналом сразу идёт SMS, без ожидания таймаута.
- Маршрутизация между SMS-провайдерами по цене и качеству.
- Учёт расходов на SMS по продюсерам (showback).

**ASR-7. Наблюдаемость**
- Единый `notification_id` и W3C trace-context в заголовках сообщений Kafka и вызовов провайдеров.
- Журнал переходов состояния в оперативной БД и его поток в ClickHouse для истории и отчётов.
- SLO-метрики (Prometheus) и алерты по скорости сгорания бюджета ошибок.
- Консоль поддержки: история уведомления по `notification_id` или по клиенту.

## 6. Архитектурные решения, которые НЕ подходят

| ID | Решение | Нарушает | Почему |
|---|---|---|---|
| X-1 | **Оставить отправку в продуктовых сервисах** (общая библиотека или прямые вызовы провайдеров) | ASR-1, ASR-3, ASR-7 | Нет единого места для состояния, failover и дедупликации: каждый сервис повторяет логику по-своему. Именно это сейчас и даёт задержки, дубли и отсутствие контроля. Синхронный вызов провайдера в транзакции платежа связывает доступность платежей с доступностью SMS-шлюза |
| X-2 | **Одна общая FIFO-очередь для всех типов уведомлений** | ASR-2, ASR-5 | Head-of-line blocking: кампания на 1 млн, отправленная за 30 мин, занимает очередь, и списание ждёт за сотнями тысяч рекламных сообщений. Приоритеты внутри одной FIFO-очереди Kafka не реализуются |
| X-3 | **Одновременная отправка во все каналы** (push + SMS + email сразу) | ASR-6, ASR-3 | Задержка и гарантия хорошие, но SMS отправляется на каждое транзакционное: оценочно до 6 млн SMS в сутки вместо около 1,7 млн (RFC, «Расчёт нагрузок»), то есть примерно в 3,5 раза больше. Каждый клиент с работающим push получает два-три одинаковых уведомления, жалобы растут, а не падают на 30% |
| X-4 | **Таймеры ожидания и повторы в памяти процесса** (`asyncio.sleep`, планировщик внутри пода) | ASR-1 | При рестарте или переезде пода (деплой, OOM, отказ узла) все ожидающие таймеры теряются вместе с уведомлениями. Каждый деплой в пиковый час создаёт недоставленные транзакционные уведомления, и никто этого не замечает |
| X-5 | **Redis как единственное хранилище состояния доставки** | ASR-1, NFR-3 | Асинхронная репликация и `appendfsync everysec` допускают потерю последней секунды записей при отказе мастера. RPO = 0 не выполняется. Подходит для кеша и rate limit, но не для источника истины |
| X-6 | **Распределённая транзакция (2PC/XA) между БД и брокером** | ASR-2, ASR-1 | Kafka не участвует в XA-транзакциях. Координатор 2PC добавляет блокирующие раунды и становится точкой отказа. Outbox даёт ту же атомарность без распределённой блокировки |

## 7. Неопределённости и архитектурные риски

| ID | Что неизвестно | Чем грозит | Как проверить |
|---|---|---|---|
| U-1 | **Распределение времени прихода подтверждения push** (ack из приложения) по iOS и Android, а также доля push, которые не подтверждаются вовсе (энергосбережение, выключенные уведомления в ОС, удалённое приложение) | Неверный таймаут push: либо лишние SMS и дубли, либо нарушение NFR-2 | Пилот: SDK подтверждений в приложении, отправка части транзакционных только по push без отправки резервного канала. По гистограмме задержки ack выбрать таймаут, при котором приходит 98% подтверждений. Срок — 2 недели, срезы по ОС и версиям приложения |
| U-2 | **Реальная стабильность и контракты SMS-провайдеров:** квоты (TPS), время прихода DLR, поддержка идемпотентности по client message id, API запроса статуса | Без идемпотентности и запроса статуса повтор через другого провайдера даёт дубль. Медленные DLR растягивают failover на email | Изучить договоры и API; нагрузочный и хаос-тест в песочницах провайдеров; исторические данные команд, которые уже отправляют SMS |
| U-3 | **Пиковый профиль транзакционной нагрузки** (дни зарплат, распродажи, выплаты), а не среднее значение | Допущения о пике в RFC («Расчёт нагрузок») могут занижать нагрузку. Есть риск не выдержать NFR-1 | Взять из процессинга поминутную гистограмму транзакций за год и найти максимум за минуту; нагрузочный тест на ×2 от найденного пика |
| U-4 | **Регуляторные требования:** обязательные каналы для отдельных операций, срок хранения журнала уведомлений, требования к согласию на рекламу | Может потребоваться другая политика отключения (§0.1) или другой срок хранения истории | Запрос в юридический отдел и комплаенс до финализации RFC |
| U-5 | **Доля клиентов без push-канала или со старой версией приложения без SDK подтверждений** | Для них push нельзя подтвердить. Либо всегда SMS (стоимость), либо слабее гарантия | Мобильная аналитика: доля активных токенов и версий приложения; прогноз обновления |
| U-6 | **Пропускная способность выбранного хранилища состояния** при 1 000 уведомлений/с (около 11 000 записей строк/с, RFC, «Расчёт нагрузок»), а также задержка CDC-ретранслятора (outbox relay) под нагрузкой | Хранилище может стать узким местом и нарушить NFR-1 | Нагрузочный тест прототипа на ×2 пика с реальной схемой; измерить p99 транзакции и задержку CDC. Заранее подготовить план шардирования |

Подробнее о рисках подсистемы гарантированной доставки — в RFC, раздел [«Риски, допущения и открытые вопросы»](docs/rfc-001-guaranteed-delivery.md#риски-допущения-и-открытые-вопросы).
